  - `FW/rules/06_문구은행.md` — 산출근거 등 상투 문구를 고를 때(결재본 빈도순, 토지·건물 구분). 새 결재본 기록 후 빈도 갱신
  - `FW/rules/05_샘플오류노트.md` — 검산 경고(B)가 떴을 때, 그 유형이 알려진 결재본 오류인지 확인할 때

## 절대 규칙
- **숫자를 머리로 계산하지 않는다.** 총여신비율, 대출가능금액, 이자수익, 편중합계, 금융비용, 타당성 산식은 `calc.py` 결과만 쓴다.
- **질문 전에 문서를 만들지 않는다.** `render_docx.py`는 A등급 누락이 있으면 스스로 멈춘다. `--draft`는 사용자가 "일단 초안"이라고 했을 때만 쓴다.
- 재료에 없는 값은 null로 둔다. 추정하지 않는다. 사업자번호, 점수, 금액을 지어내면 안 된다.
- 웹검색은 **업계전망에만**, 그것도 사용자가 허용했을 때만 쓴다. 담보물 개요는 재료에서만 가져온다.
- 결재본 샘플의 문구를 복붙하지 않는다. 원자료가 기준이다.

## 절차

### 1. 재료 목록 만들기
첨부된 파일을 전부 읽고, 아래 표를 사용자에게 보여준다.

| 파일 | 자료종류 | 이 자료로 채우는 칸 |
|---|---|---|

자료종류: 대출사전검토의견서 / 신용평가결과 / 사업자등록증 / 소득금액증명원 / 부가세과세표준증명 / 지방세세목별과세증명 / 표준재무제표증명원 / 감정평가서 / 탁상감정 회신 / 인포케어 캡처 / 등기부등본 / 원천징수이행상황신고서 / 임대차계약서 / 기타
- `.hwp`는 읽을 수 없다 → PDF로 저장해서 다시 달라고 요청한다.
- 스캔 이미지는 숫자를 두 번 읽어 대조한다(금액·면적·점수).

### 2. case.json 초안
- `FW/cases/<YYMMDD>_<채무자>/case.json`을 `FW/cases/_template/case.json`에서 복사해 채운다. 필드 설명은 `FW/cases/예시_업체J/case.json`을 본다.
- 금액은 **원**, 담보물 평가액·재무는 **백만원**, 면적은 ㎡ 숫자로 넣는다.
- 금융거래 각 건에 `용도`(운전/시설/가계/기타), `동일담보`, `증액대상`, `대환대상`을 반드시 표시한다. 계산이 여기에 달려 있다.
- 서술(업체전망, 긍정/부정, 입지/교통/공법)은 사전검토의견서 문장을 규칙에 맞게 다듬어서 넣는다.
- **적법성 조항은 자료에 적힌 조항·번호를 그대로** `적법성.자료조항`에 옮긴다(문체만 심사의견서식으로). 번호가 이상하거나 자료끼리 다르면 그때 질문한다.

### 3. 작성 전 질문 (핵심)
```
python "FW/scripts/calc.py" "<case.json>" --gaps
python "FW/scripts/calc.py" "<case.json>"          # 핵심 숫자 미리보기
```
결과를 `03_질문목록.md` 프로토콜대로 **한 번에** 묻는다.
- 먼저 핵심 숫자 미리보기 3줄을 보여준다(표B, 편중합계, 이자수익). 사용자가 숫자부터 확인할 수 있게 한다.
- **A 필수**와 **B 충돌**은 번호 목록으로 묻는다. B에는 "샘플에서 실제로 났던 오류 유형"이라는 설명을 붙인다.
- **C 보완**은 "있으면 올려주세요, 없으면 공란으로 둡니다"라고 한 묶음으로 묻는다.
- **D 판단**은 `AskUserQuestion`으로 묻는다(자료에 없는 조항 후보는 multiSelect, 업계전망 근거, 신용위험 섹션). 한 번에 4개까지.
- 답을 반영해 `--gaps`를 다시 돌린다. `READY`가 나올 때까지 반복하되, 최대 2라운드로 끝낸다.

### 4. 작성과 검수
```
python "FW/scripts/render_docx.py" "<case.json>"
python "FW/scripts/to_pdf.py" "<생성된 .docx>"
```
- PDF를 Read로 열어 표가 깨지지 않았는지, 빈 칸이 없는지, 쪽수가 4쪽 안팎인지 눈으로 확인한다.
- 사용자에게 보고할 것:
  1. 파일 경로(docx, pdf). SendUserFile로 docx를 보낸다.
  2. 핵심 수치(대출가능금액, 총여신비율, 편중합계, 이자수익)
  3. 남은 검산 경고(B)
  4. 미확보 항목(C 잔여) — 결재 전에 사람이 채울 칸
  5. 자료에서 라이브러리에 없던 조항이 나왔다면 `02_규정조항_라이브러리.md`에 추가하고, 추가했다고 보고

### 5. 피드백 반영
사용자가 규칙을 고치라고 하면:
1. `01_작성규칙.md` / `02_규정조항_라이브러리.md`를 고친다.
2. 문구·조건이 바뀌면 `calc.py`의 `LIB` / `APPROVAL` / 트리거도 같이 고친다.
3. `python "FW/tests/regression.py"`를 돌려 **ALL PASS**를 확인한다. 결재본과 달라지는 게 의도된 변경이면 기대값을 고치고 이유를 주석으로 남긴다.
4. 새 결재본이 생기면 `tests/regression.py`에 케이스를 추가한다.

### 6. 학습 로그 (건이 쌓일수록 초안이 나아지게)
- **결재가 끝난 건을 받으면 반드시 기록한다.** 사용자가 최종 결재본(.docx 또는 .pdf, hwp면 PDF 변환 요청)을 주면:
  ```
  python "FW/scripts/learn.py" record "<case_dir>" "<결재최종본.docx|.pdf>"
  ```
  초안과 결재본을 문단·표 단위로 비교해 `FW/learning/diffs.jsonl`(수정 내역)·`scorecard.jsonl`(건별 질문 수·수정 건수)에 쌓는다.
- 세션 시작 시 `FW/learning/candidates.md`가 있으면 먼저 훑는다. 이미 2건 이상 반복된 수정 패턴이 있다는 뜻이다.
- 새 건 기록 후 `python "FW/scripts/learn.py" candidates`로 후보를 갱신하고, 사용자에게 **간단히** 보여준다("이번에 N번째로 같은 수정이 나왔습니다 — 규칙에 반영할까요?").
- 사용자가 승인하면: ① 규칙 파일을 손으로 고친다(위 5번 절차) ② `python "FW/scripts/learn.py" close <id> approved`로 닫는다.
- 반려하면 `close <id> rejected`로 닫아 다시 제안되지 않게 한다.
- **규칙을 스스로 바꾸지 않는다.** candidates.md는 제안일 뿐이고, 반영은 항상 사람 승인 후 수행한다(과최적화 방지 — `analysis-framework` 원칙과 동일).
- `python "FW/scripts/learn.py" score`로 누적 추이(건별 A/B/C/D 질문 수, 수정 건수)를 확인할 수 있다. 사용자가 진행 상황을 물으면 이걸로 답한다.
